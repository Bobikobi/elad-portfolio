### Analysis of Colour-Space Issues & Contradicted Findings

#### 1. Colour-Space Analysis
- **`earth_clouds.webp` at [`SolarAct.tsx:555`](../../src/components/scene/acts/SolarAct.tsx#L555)**:
  - **Is it actually wrong?** **Yes.** `earth_clouds.webp` is a grayscale alpha/density mask sampled in `earthCloudFrag` as `float c = texture2D(uMap, vUv).r;`. Annotating a scalar data texture with `THREE.SRGBColorSpace` triggers hardware sRGB-to-linear decoding on sampling, which applies an approximate power curve of $x^{2.2}$. This artificially compresses low- and mid-density cloud values (e.g. a density of 0.35 is crushed to ~0.098).
  - **What changing it moves on screen**: Removing `colorSpace: THREE.SRGBColorSpace` restores linear evaluation. Mid-tone cloud densities will increase significantly, expanding cloud coverage, making thin cirrus and tropical fields visible and continuous, and softening harsh cloud boundaries on Earth's day side without changing texture files.
- **`softSprite()` at [`spaceMaterials.ts:42`](../../src/lib/spaceMaterials.ts#L42)**:
  - **Is it actually wrong?** **No (visually inert).** In `softSprite()`, the canvas radial gradient writes `rgba(255, 255, 255, a)` at every stop. The RGB channels are uniformly 1.0 (255), and the gradient is carried entirely in the alpha channel. In WebGL / three.js r185, `SRGBColorSpace` only transforms RGB channels; the alpha channel is mathematically linear regardless of colour space. Transforming an RGB of $(1.0, 1.0, 1.0)$ through sRGB-to-linear yields $(1.0, 1.0, 1.0)$.
  - **What changing it moves on screen**: Changing `_soft.colorSpace` to `NoColorSpace` moves **zero pixels** on screen across all consumers (`Nebula`, `Sun`, `DiveObjects`, `GalaxyDetail`). It should be updated solely for architectural cleanliness.
