   Afterwards write `<id>-verify.md` with an adversarial self-check listing at least three
   ways the result could be FALSELY passing, each actually tested. Update
   `docs/briefs/INDEX.md`. Never back-date a brief; if one is written after the fact, label
   it as such.
2. **Numbers only from a deployed preview alias**, never from localhost, never from a bare
   deployment hash.
3. **Never force-push a shared branch without asking.** A truncated commit message is not
   worth rewriting history over.
4. **Verify a deploy by a value the new build actually changes**, never by elapsed time.
   Two verification rounds read a stale deploy before this became a habit.
5. **Check the instrument before believing the reading.** Harness defects that produced
   confident false reports so far: a summed-area table missing its zero row (reported zero
   stars on a sky full of them), masking full-viewport DOM layers (masked the entire sky),
   tracking points at fixed coordinates while debris moves through them (99.8% "flicker"),
   a shared browser profile leaking a stored locale into the next case, sampling before
   hydration (45 nulls that looked like a feature that never ran), and reading a settled
   value from the first sample.
6. **The measurement wins over the expectation**, including over a reviewer's hypothesis and
   over your own. Say so plainly when it does.
7. **Do not touch** CameraRig's state machine, the act-swap system or the quality governor
   unless the task explicitly says so. (`publishLimb` is an approved exception: read-only,
   ORBIT branch only, never writes position/quaternion/fov.)
8. **`git add <path>` explicitly. Never `git add -A`.**
9. Commit/push when the work is done; **merging to `master` is the owner's**.

### 1. PROJECTS-HOVER
Project windows must be **preview-only**: the image fills the window, no text inside it. On
hover (desktop) the description appears as a floating overlay near the planet - title,
description, tech chips, in the glass surface tokens - following the hovered window and
disappearing on leave. With no pointer, the overlay shows the centred/first window's text so
the page is never text-empty; the full text stays in the DOM (visually hidden at most) for
crawlers and screen readers. Touch: **tap once shows the overlay, tap again enters the
project**. All three locales.

**This behaviour already exists**, built as B8d on `feat/b8c` - reconcile that work into the
current live layout rather than rebuilding it. Cherry-pick or port, whichever is cleaner
given the branch state, and close the superseded branch with a note.

Acceptance: a desktop hover recording showing the overlay following the pointer smoothly and
zero text inside windows; the touch flow verified at 390x844; text present in the DOM for all
12 projects; no regression to click-to-enter or to scrolling.

### 2. SUN-2 - the sun reads smooth against the reference imagery
In order of visual weight:
1. **Granulation** - a high-frequency detail octave on top of the existing large turbulence:
   1-2 noise octaves at roughly 8-15x the current frequency, low amplitude, flowing slowly.
   The surface currently has only the large soft blotches; the fine grain is what makes a
   photographed sun read as boiling rather than smooth.
2. **Limb darkening** - an N-dot-V falloff on the emissive, about 25-35% at the limb. This
   one term adds the sphericity the flat disc lacks.
3. **Limb activity** - the edge should not be a clean circle: keep the trembling
   displacement and make the existing prominences read against dark space at the limb, a few
   arcs rising and collapsing on slow cycles.
4. **Contrast inside the disc** - slightly deepen the dark lanes between cells, without
   letting highlights clip. The tone-map discipline stands.

Tier law: identical composition on all tiers; the extra octaves are shader maths, not new
passes - **verify the render count per frame is unchanged**. Acceptance: an overview sun crop
side by side with the reference, showing granulation, limb darkening and an active edge; a
recording showing the fine grain flowing; renders/frame unchanged; no clipping.

### 3. Ruling still open - window count (from the external review)
2-3 windows on desktop and 1 in portrait is too few for 12 projects: a visitor cannot tell
whether there are three or thirty. **Reduce thickness until at least 3 are visible on desktop
and 2 in portrait, and add an explicit affordance that more exist** - a "3 / 12" counter or

is the harder constraint. Apply this to whatever layout is currently live, not to the older

### 4. Ruling still open - the framing model is ~3% off everywhere
`fill` in `orbitFraming.ts` sizes the sphere's TANGENT PLANE, not its silhouette, so every
framing target in the project is about 3% off: the arrival sun (35-45%), the ORBIT planet
hero (60-70%), the mobile tour stops, the belt ride. **Fix `fill` to use the true silhouette
- divide by `sqrt(1 - (R/d)^2)`** - so a stated target means what it says, then re-measure
the framing acceptances that were signed off against the old model and report any that now
fall outside their band. Nothing needs re-designing; only the measurement model corrected.

Note while doing it: there are **three** disagreeing models in the codebase. The design one
(`fill` via `tan`), the debug HUD's (`2*atan(R/d)/fovY`, the angular diameter), and the truth
(the projected silhouette, `tan(asin(R/d))/tan(fov/2)`). At the ORBIT framing these read
0.680, 0.6965 and 0.7005. Fix both the design model and the HUD, or acceptances measured
from the HUD will stay wrong by a smaller amount.
